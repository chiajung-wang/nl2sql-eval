**Step 6 follow-up (#75) — schema-token-budget retrieval crossover.** BIRD has no schema that overflows a modern context window (largest ~1.8K tokens), so this is a **controlled experiment**, not a natural-overflow claim: under a configured schema-token *budget* (a cost/latency policy), is it better to **truncate** the schema or to **retrieve** the relevant tables? On the frozen `step6-large-schema-retrieval-lift` slice, the modes **converge at 4096t** (selection divergence 0 — every schema fits, so both send the generator identical prompts). The residual +0.050 there is therefore **sampling noise**, not retrieval: generation runs at non-zero temperature, so two independent runs on the *same* prompt differ by ~0.050 (2/40 questions). Read the tight-budget gaps against that floor: the pass@1 advantage peaks at **512t (+0.100)** but is modest relative to it, so on this 40-question slice the gap is suggestive, not conclusive. RAG recall climbs 0.450→1.000 with the budget — the robust signal: more budget lets retrieval cover more of the gold tables, while truncation gets no such targeting. This is the honest other half of the Step-6 finding: where the full schema fits the budget the two modes are identical; where it does not, retrieval keeps the *right* tables and truncation cuts blindly — the recall gap is real and monotone, the pass@1 gap real but small against sampling noise. With today's context windows that budget is a policy choice, not a hard limit.

**Step 5 follow-up — what self-correction is worth, as a controlled study.** Step 5's +0.000 gap was an *eligibility* result, not a verdict on correction: the loop only feeds back **execution errors**, and the small Step-3 slice produced none. To find where the loop earns its keep, the **same twin** was run on the frozen `step6-large-schema-retrieval-lift` slice (naive full-schema dump, up to 14 tables) as a two-axis study — first a **budget sweep** (k=3, k=5) holding the strong model fixed, then a **generator swap** (strong → weak) holding the slice fixed. The model self-corrects itself; it is never swapped between attempts.

| run | model | pass@1 | pass@k | gap | eligible exec-errors | recovered |
| --- | --- | --- | --- | --- | --- | --- |
| k=3 | `claude-sonnet-4-6` | 0.725 (29/40) | 0.725 (29/40) | +0.000 | **0** | 0 |
| k=5 | `claude-sonnet-4-6` | 0.675 (27/40) | 0.675 (27/40) | +0.000 | **0** | 0 |
| k=3 | `kimi-k2.7-code` (weak) | 0.425 (17/40) | 0.475 (19/40) | **+0.050** | **5** | 2 (+7 attempts) |

**The lever is generator weakness, not schema size or budget.** With the strong model, raising the budget from k=3 to k=5 does nothing (gap +0.000 both times) because the eligible execution-error population is **0** — *every* pass@1 failure (11, then 13) was a **wrong-answer** (valid SQL, wrong result), not one execution error. The big schema didn't help: a capable model writes *syntactically valid* SQL even against 14 tables; it just sometimes selects the wrong valid columns, and error feedback can't fix a semantic mistake. Swap in the **weaker** `kimi-k2.7-code` on the *same* slice and the loop finally has fuel: **5** attempt-1 execution errors, of which it recovers **2** — pass@1 0.425 → pass@3 **0.475**, a **+0.050** gap, bought with **7 extra generate→execute cycles** and ~94s added wall-clock. (Added *dollar* cost is unpriced here: `kimi` routes via OpenRouter, whose cost the dated list table the twin prices from doesn't carry — the cross-provider table reconciles that via provider-reported cost; #52.)

**Why the +0.050 is signal, not the noise floor — and what it is *not*.** This is the distinction the twin metric exists to make. The strong-model 0.725-vs-0.675 difference is **between two independent runs**, so it is pure resampling jitter (~0.05 floor, temperature>0). The weak-model +0.050 is **within one run**: pass@1 is derived from the *same* pass@3 run's first attempts, so the 2 recovered questions are specifically ones that **errored on attempt 1 and the correction loop flipped to correct** — `recovery_rate` and the **+7 added attempts** are the causal proof the loop did the work, not a second sample. That said, this is **one weak-model run at one k (n=1)**: it is a clean *demonstration that the loop fires and recovers*, not a precise estimate of the magnitude — the **+0.050** is illustrative, and a fuller claim would need replication and a k-sweep on the weak model. The honest synthesis stands: **self-correction is worth roughly the execution-error rate × the recovery rate**, so its value rises with how malformed the generator's SQL is — near-zero for a strong model (0 errors to feed back), demonstrably non-zero for a weak one — and the twin reports that lift *with its retry price*, never as a bare headline. Reproduce with `uv run python -m eval.eval_bird_selfcorrect` (sweep `RETRY_BUDGET`; set `MODEL=openrouter/moonshotai/kimi-k2.7-code` for the weak-generator row).
