nl2sql-eval

A guardrailed agentic Natural-Language-to-SQL system — built as a case study in rigorously evaluating and operating an LLM system.

The one sentence that explains everything: the NL-to-SQL agent is the workload; the eval harness, observability, and prompt-CI/CD wrapper around it is the product. Anyone can wire an LLM to a database — the point here is to prove it works, catch when it breaks, and operate it day to day.

If you remember nothing else: the measurement apparatus is the centerpiece. eval/ is a peer of src/, never subordinate. Features are not claimed, they are measured — scored against frozen benchmarks and red-team fixtures, with every reported number traceable to its exact config and commit.

2 · The mental model

Hold three layers in your head. They map directly onto the directory tree.

LayerWhat it isLives in
The workloadAn instrumented NL→SQL pipeline (a state machine). Takes a question, returns a verified result.src/nl2sql/pipeline/
The productThe eval harness that drives the pipeline over frozen question slices and scores it. The reason the repo exists.eval/
The evidenceGolden + red-team fixtures, and RESULTS.md — every number tied to model, slice, prompt version, date, commit.fixtures/, RESULTS.md

Import-sharing is non-negotiable. Both the eval harness and the demo UI import the same compiled pipeline. The pipeline is never forked or duplicated — so there is zero drift between what is measured and what is shown to a user.

3 · The pipeline (the system under test)

The pipeline is a state machine with conditional edges. One stage per module under src/nl2sql/pipeline/ — they are never collapsed into one file.

retrieve→ generate→ guard→ soundness→ literal_check→ execute→ correct↺ redact
StageModuleWhat it does
retrieveretrieve.py
link.py		Schema-RAG over table/column metadata + sample values (retrieval over schema, not documents). Loop-aware. Step 12: an alternative task-alignment linker (link.py) selectable by config — harvest the tables the generated SQL references rather than scoring/dropping tables.
generategenerate.pyLLM SQL generation, using an externalized prompt template.
guardguard.pyDeterministic sqlglot AST checks, pre-execution: read-only enforcement, dangerous-op blocking, cost/complexity heuristic, per-db table-scope. No regex, no LLM. A hit is a terminal reject (safety gate).
soundness
literal_check		soundness.py
literal_check.py		Step 12. Same AST-check shape as the guard, opposite contract: a hit is a correction signal, not a reject. soundness flags bad-construction patterns (NULL-ordering hazard, min/max-by-subquery, field catenation); literal_check flags a literal bound to the wrong column (via a sampled value index). With budget they feed back to generate; with the budget spent the candidate executes anyway — a false positive costs a wasted retry, never a dropped run.
executeexecute.pySQLAlchemy execution, multi-engine (SQLite for BIRD, Postgres for payments).
correctcorrect.pyFeeds execution errors / retrieval misses / soundness / literal signals back into regeneration — within a capped retry budget.
redactredact.pyColumn-aware, deterministic, schema-driven PII masking. Runs after scoring.

Shared run state and the terminal-state enum live in state.py. The graph wiring lives in graph.py (a LangGraph graph). The smallest possible loop is runnable as a smoke check:

uv run python -m nl2sql.pipeline.graph "How many users are based in the US?"

4 · Two exits — and why scoring happens before redaction

This is the crux of the whole design. The pipeline has two distinct exits:

EXIT 1

Raw verified result

The unredacted result. This is what the harness scores against gold — upstream of redaction. Scoring is canonicalized result-set comparison, never SQL string-match (two different queries can be equally correct).

EXIT 2

Presented result

Post-redaction. The only thing ever shown to a user or written to a log, trace, or span. Raw PII never reaches a log line.

Why the order matters: if redaction ran before scoring, masked PII would corrupt the comparison and silently invalidate every reported number. So: score the raw result, then redact for presentation. Redaction must never touch the scoring path.

5 · Terminal states

Every run buckets into exactly one terminal state. This is how failures are categorized in the eval.

StateMeaning
successResult matches gold.
wrong_answerExecuted cleanly but the result-set doesn't match gold (a semantic miss).
retry_exhaustedBurned the retry budget without recovering.
execution_error_finalSQL still errors after correction attempts.
guardrail_rejectedGuard blocked the query pre-execution.
retrieval_emptyRetrieval returned nothing usable.

Critical boundary: the enum lives in state.py; the classifier that assigns the state lives in the harness — never in state.py. The pipeline carries state; the harness interprets it.

6 · The eval harness (the product)

eval/harness.py is the batch runner: it drives the import-shared pipeline per question over a frozen slice, scores against gold, buckets the terminal state, and records cost/latency/attempts. The thin eval/eval_*.py entrypoints are each a different experiment over that one runner.

Entry pointWhat it measures
eval_bird.pypass@1 baseline on the frozen BIRD slice (naive schema dump).
eval_bird_twin.pyThe twin metric: pass@1 vs pass@k — what self-correction is worth, and the cost the gap buys.
eval_bird_selfcorrect.pyThe twin on a large-schema slice, with a selectable generator (MODEL env var).
eval_bird_rag.pyNaive-dump vs schema-RAG retrieval lift, plus retrieval recall. Also the A/B host for the Step-12 env axes (LINK_STRATEGY, METADATA_SOURCE, LITERAL_STEER, SOUNDNESS, RETRY_BUDGET).
eval_bird_vote.pyStep 12: the majority-voting twin — attempt-1 vs pass@k-majority over k field-order-shuffled candidates, plus the vote-agreement distribution. Reuses the comparator as a candidate selector.
eval_bird_minidev.pypass@1 (schema-RAG) over BIRD's own curated, difficulty-stratified 500-question Mini-Dev slice (slice_minidev.py) — same 11 dbs as the rest of BIRD, adopted whole rather than resampled, with its community-corrected gold SQL. Every run auto-triages its non-success cases (reusing diagnose_bird's deterministic sqlglot-AST taxonomy) into a gold-vs-candidate failure report — no separate diagnose pass needed.
diagnose_bird.pyFailure analysis: for every wrong answer, a deterministic, sqlglot-AST-derived tag for the likely root cause (table/join mismatch, missing GROUP BY, aggregate mismatch, …) — a taxonomy, not just a pass/fail count. No regex/LLM for the tagging.
eval_cross_provider.pyCross-provider table: accuracy × cost × latency per model (via LiteLLM).
redteam.pyGuardrail catch rate against the red-team fixture — deterministic, no model needed.
eval_payments.pyThe same machinery against the Postgres payments demo set.

Twin reporting (pass@1 AND pass@k) is mandatory — the gap quantifies what self-correction is worth. Retrieval runs additionally report retrieval recall against the gold query's actual tables.

Each step also ships a self-contained proof that runs offline where possible: prove_step1.py (one seed question → result vs gold), prove_step8.py (renders an example trace), prove_step9.py (replays the prompt-CI regression delta).

7 · Guardrails & the comparator (the deterministic cores)

Two pieces of the system are deterministic by law — no LLM calls, no regex for SQL semantics, sqlglot ASTs only. They are the most heavily tested code in the repo because a bug in either silently corrupts results.

The comparator — eval/compare.py

Canonicalizes result sets and compares them. This is how a run is scored. Must pass its entire golden fixture of (gold, candidate, expected_verdict) triples. Its rule set is audited against the official BIRD evaluator (see docs/eval/comparator-rule-set.md).

The guard — src/nl2sql/pipeline/guard.py

Four deterministic AST checks, pre-execution: read-only enforcement (block writes/DDL), dangerous-op blocking, cost/complexity (heuristic-first), and per-db table-scope. On fail it either rejects or feeds back as a correction signal. Measured against the red-team fixture (reported catch rate).

Test discipline: add a golden-fixture case for every new comparison edge case; add a red-team case for every new dangerous-query pattern. Run them with uv run pytest tests/test_compare.py tests/test_guard.py.

8 · Fixtures & the results log

Fixtures are deliverables, not test scaffolding

  • fixtures/golden_compare/ — (gold, candidate, expected_verdict) triples that prove the comparator.
  • fixtures/redteam_guard/ — injected dangerous queries (read-only, dangerous-op, cost, table-scope, prompt-injection) that measure the guard.

RESULTS.md — the running results log

A step is not done until its number is appended to RESULTS.md with the exact config: model, slice ID, prompt version, date, the number, and the commit. Never report an eval number without a corresponding entry. Every number must be traceable to the config and commit that produced it.

11 · The invariants (what you must never break)

These are the rules that keep the apparatus honest. They live in CLAUDE.md / the PRD; internalize them before editing.

  • Execution accuracy via canonicalized result-set comparison — never SQL string-match.
  • Score upstream of redaction — redaction runs afterward and must never corrupt scoring.
  • Raw PII never reaches logs/traces/presented output — only the redacted result is ever shown or logged.
  • Guardrails & comparator are deterministic — sqlglot ASTs only; no regex for SQL semantics, no LLM-as-judge as the primary scorer.
  • One pipeline stage per module; the pipeline is import-shared by harness and demo — never forked.
  • Terminal-state classifier lives in the harness, the enum in state.py.
  • Step-12 boundaries: profiling-derived field descriptions are generate-prompt content only — never read by the guard or comparator, and PII columns are profiled shape-only (no raw values). Majority voting reuses eval/compare.py read-only — no second equivalence implementation. Soundness / literal checks are correction signals, never terminal rejects.
  • Prompts are externalized in prompts/ as templates — never inlined in Python (CI diffs that directory).
  • Self-correction is capped by a retry budget.
  • Report twin metrics (pass@1 AND pass@k) and retrieval lift/recall — not just overall accuracy.
  • Every reported number → a RESULTS.md entry with model, slice, prompt version, date, number, commit.
  • Eval slices are frozen, seeded, stratified — repeatability is a feature.
  • Out of scope: cross-db routing, open-ended generation eval, LLM-as-judge-as-primary-scorer.
  • Never add Claude / Claude Code as author or co-author on commits or PRs.

12 · Getting it running

# 1. Install deps (uv reads pyproject.toml, creates the virtualenv)
uv sync

# 2. Configure
cp .env.example .env       # edit with provider key + DB URLs

# 3. Verify the deterministic cores pass FIRST (no API key needed)
uv run pytest tests/test_compare.py tests/test_guard.py

# 4. Guardrail catch rate — deterministic, no model
uv run python -m eval.redteam

# 5. Offline proof — one seed question end-to-end
uv run python -m eval.prove_step1

# --- live runs below need a provider key ---

# pass@1 baseline on the frozen BIRD slice
uv run python -m eval.eval_bird

# pass@1 on the 500-question Mini-Dev slice (schema-RAG), auto-triaged
MODEL= RUN_CONFIG=accuracy uv run python -m eval.eval_bird_minidev

# the demo UI (isolated dep group)
uv sync --group demo
uv run streamlit run apps/demo/app.py

Configuration is via environment variables (an .env file): ANTHROPIC_API_KEY / OPENROUTER_API_KEY for generation, PAYMENTS_DB_URL for the demo, BIRD_DATA_DIR for BIRD runs, the two LANGFUSE_* keys for tracing, plus optional MODEL, MAX_TOKENS, RUN_CONFIG, SLICE, RETRY_BUDGET. The Step-12 levers are A/B axes, each off/baseline by default so a clean run is unchanged: LINK_STRATEGY (task-alignment linking), METADATA_SOURCE (supplied / profiling / fused), LITERAL_STEER, SOUNDNESS, VOTE_K. Live model runs can be deferred — much of the system proves itself offline.

13 · Where to look first

A reading order for a new contributor:

  1. docs/prd.md — the product requirements everything derives from.
  2. ../README.md — the front door, with the headline findings and full config reference.
  3. src/nl2sql/pipeline/state.py then graph.py — see the run state and how the stages are wired.
  4. eval/harness.py — the batch runner and terminal-state classifier (the product's heart).
  5. eval/compare.py + tests/test_compare.py — how scoring actually works.
  6. src/nl2sql/pipeline/guard.py + tests/test_guard.py — the deterministic guard.
  7. docs/plans/step-N/ and docs/blogs/ — the narrated build, step by step, if you want the rationale behind each piece.
  8. ../RESULTS.md — every committed number and the config that produced it.
