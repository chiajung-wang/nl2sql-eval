1 Overview

The thinnest end-to-end slice of the measurement core — the comparator skeleton every later Step-2 slice extends.

This PR lands the public compare() entry point in eval/compare.py: a deterministic result-set scorer that compares values, never SQL strings (CLAUDE.md §5.1, §7). It ships only the trivial "exact" rule, but does so through a configurable canonicalization-rule pipeline — each rule is applied to both sides before comparison, so a rule can never make a wrong answer look right, and the applied rules are recorded on the verdict and logged per call.

Crucially, it lands the proof harness alongside the scorer: a committed golden fixture of (gold, candidate, expected_verdict) triples and a fixture-driven test that treats those triples as the source of truth. A number from an unvalidated scorer is worse than no number, so the proof comes first.

2 Key changes

compare() — the public scorer

  • Returns a Comparison carrying a clear Verdict (correct / incorrect), the applied rules, and a human reason.
  • Compares result-set values only — not the SQL string, and (in this slice) not column labels: a correct value under a different alias is still correct.
  • gold_sql is recorded for explainability; the order-insensitivity rule (Issue #12) will inspect it for ORDER BY.

Canonicalization pipeline

  • Rules register by name via register_rule() and are applied to both sides in order.
  • Ships "exact" only; the subtle rules (ordering, NULL/float/column, multiset, BIRD alignment) slot in for Issues #12–#14 without touching compare().
  • An unknown rule name is rejected with a ValueError.

Empty result — a distinct case

  • Both-empty → correct (a legitimately empty answer, not an error).
  • Empty vs non-empty (either direction) → incorrect; empty is never auto-correct.

PII-safe logging

  • Logs verdict, applied rules, reason, and gold_sql — never the result rows.
  • The comparator runs upstream of redaction (§5.2), so logging row values would leak raw PII into traces (§5.3).

Golden fixture — the deliverable

  • baseline.json: 8 triples — identical, plainly-different, alias-rename, multi-row, missing-row, and the three empty-result permutations.
  • Self-documenting _meta block + README describing the case format and the rules override.

Fixture-driven tests

  • Loads every *.json in the fixture dir — adding a triple is exercised automatically, no test edits.
  • A non-empty-fixture guard prevents a glob/parse regression silently turning the proof into a no-op.
  • Contract tests: unknown-rule rejection, applied-rules logged, value-based-not-name-based verdict.
