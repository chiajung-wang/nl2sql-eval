1 Overview

The value- and shape-level rules that let two differently-written-but-equally-correct queries compare equal — while still catching real semantic errors.

Each rule is a deterministic transform registered into the same canonicalization pipeline as Issues 11–12, applied to both sides before comparison, so a rule can only let an equally-correct query pass — it can never make a wrong answer look right (CLAUDE.md domain rule 1). No LLM, no regex for SQL semantics.

Three new always-on rules join the default pipeline — column_position, null_sentinel, float_tolerance — and multiset semantics come for free by omission: there is deliberately no de-dup rule, so a COUNT vs COUNT DISTINCT row-multiplicity difference stays a real error.

2 The rules

column_position — match by position, not name

  • Replaces column labels with positional placeholders, so an alias/rename/relabel of an otherwise-correct query cannot fail it.
  • A genuine column-order error (values transposed between positions) still differs → caught.
  • Inert by design against the current value-only comparison; it names and logs the position-based contract and is the seam for a future label-aware rule.

null_sentinel — one normal form for NULL

  • Every SQL NULL (None) collapses to a single sentinel, so NULLs compare consistently and become hashable / orderable for downstream rules.
  • The sentinel is distinct from any real value — a NULL never silently equals 0, "", or the string "None".

float_tolerance — round before comparing

  • Floats / Decimals are rounded to FLOAT_DECIMALS = 6 places, so insignificant precision noise (an AVG differing in the 9th digit) doesn't read as wrong.
  • A genuinely different number still differs → caught. bool (an int subclass) is left untouched, not rounded to 0/1.
  • A fixed, logged constant — not a per-call knob — keeps every verdict reproducible.

Multiset semantics — by omission

  • There is no de-dup rule, so two results differing only in row multiplicity stay distinct.
  • The classic COUNT vs COUNT DISTINCT bug → incorrect. Set semantics would wrongly pass it.
  • A future set rule would be the canonicalization; its absence is what makes the comparator multiset.

Value normalization runs before order_insensitive on purpose: that rule sorts rows by their stringified cells, so floats must already be rounded and NULLs normalized — otherwise the same logical rows could sort differently on the two sides and a correct answer would be judged wrong.
