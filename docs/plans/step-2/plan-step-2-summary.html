1 Headline & goal

Prove the scorer is trustworthy before trusting any number it produces.

Build the result-set comparator with explicit, committed canonicalization, plus a checked-in golden fixture that proves the canonicalization is correct. A number from an unvalidated scorer is worse than no number — this step is the precondition for Step 3 meaning anything. The comparator is one of the two deterministic correctness cores (alongside guard.py) and must pass its entire golden fixture (CLAUDE.md §8, PRD §5).

2 What to build

eval/compare.py — canonicalize then compare

  • Row ordering: sort rows before comparing unless the gold SQL has ORDER BY — then order is part of correctness and must NOT be sorted away.
  • Column matching: by position, not name (aliases/renames must not fail a correct query).
  • NULL handling: normalize to a sentinel.
  • Float tolerance: round to a fixed tolerance.
  • Duplicates: multiset semantics by default (catches COUNT vs COUNT DISTINCT as real errors).
  • Empty result: a distinct, correct-able case.
  • BIRD alignment: where ambiguous, match BIRD's official evaluator so numbers stay leaderboard-comparable.
  • Rules are configurable and logged per comparison.

fixtures/golden_compare/ — named deliverable

  • Hand-built (gold_result, candidate_result, expected_verdict) triples — not throwaway test data.
  • Covers each hard case: order with/without ORDER BY, multiset vs set, NULL sentinel, float tolerance, column rename/reposition, empty result.
  • The artifact you point at in interviews: "here's how I know my scorer is correct."

tests/ — fixture-driven

  • Tests for compare.py are driven by the golden fixture.
  • Add a fixture case for every new comparison edge case (CLAUDE.md §8).
  • uv run pytest green; lint/format clean.

Both result sets pass through the same deterministic canonicalize() before comparison; the gold SQL's ORDER BY decides whether row order is preserved. The golden fixture asserts the verdict for every hard case — passing the entire fixture is the Step's definition of done.

5 Pitfalls

PitfallSeverityWhy it bites
ORDER BY conditional subtle Getting it wrong creates false negatives (sorting away real order errors) or false positives. The trickiest rule in the module.
Undersizing the step timeline Budget real time — this is not a quick afternoon. It's the module that can silently invalidate every reported number.
"BIRD-aligned" as assertion credibility "BIRD-aligned" is just a claim until the fixture proves it case by case.

6 Guardrails for this step

Never (anti-patterns)

  • Compare SQL by string-match — result-set comparison only (CLAUDE.md §7).
  • Use an LLM judge or regex as the scorer — the comparator is deterministic.
  • Report a number without a RESULTS.md entry (applies from Step 3).

Always

  • Keep eval/ a peer of src/.
  • Make canonicalization rules explicit, configurable, and per-comparison logged.
  • Add a fixture case for every new comparison edge case.
