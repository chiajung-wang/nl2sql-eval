order-sensitivity — the ORDER BY conditional

1 Overview

The subtle, false-negative-prone canonicalization rule: row order is normalized away — unless the gold query says it matters.

This PR adds the order_insensitive rule to the comparator pipeline from Issue #11 and makes it the new default. Two queries returning the same rows in a different order are equally correct, so rows are sorted on both sides before comparison — except when the gold SQL declares a top-level ORDER BY, where the order is the answer and a same-rows/wrong-order candidate must be judged incorrect.

Detection is sqlglot AST-based, never regex (CLAUDE.md §4): it reads the order arg off the outermost SELECT / set-operation node, so an ORDER BY buried in a subquery, derived table, or CTE body is correctly ignored — and an ORDER BY inside a string literal never false-positives. A new RuleContext threads gold_sql through the pipeline so the rule can branch on it while still being applied identically to both sides — sorting can never launder a wrong answer.

2 Key changes

order_insensitive — the new default rule

  • Sorts rows on both sides before comparison so row order is normalized away when it is not significant.
  • Gated on ctx.gold_sql (never the candidate's): a significant ORDER BY leaves rows untouched.
  • DEFAULT_RULES moves from "exact" → ("order_insensitive",); "exact" stays available for opt-in.

AST-based ORDER BY detection

  • _gold_order_is_significant() parses with sqlglot.parse_one and reads args["order"] off the outermost node.
  • Subquery / derived-table / CTE-body ORDER BY → not significant; set-op + post-CTE top-level → significant.
  • Unwraps a parenthesized whole query (SELECT … ORDER BY …) so its order stays top-level.

RuleContext threaded through the pipeline

  • New frozen RuleContext(gold_sql=…) passed identically into the rule for both sides.
  • Rule signature becomes (ResultSet, RuleContext) → ResultSet — a branch on context can't make a wrong answer look right.

Total, exception-free sort key

  • _row_sort_key() maps each cell to (null_rank, type_name, str(value)) so heterogeneous / NULL cells never raise.
  • Used only to align equal multisets for comparison — it is not value canonicalization (NULL/float is Issue #13) and never collapses distinct rows.

Golden fixture — proves it both ways

  • order_sensitivity.json: significant wrong/right order, no-order reordering, subquery ORDER BY, multi-column, and a wrong-answer-can't-be-laundered guard.
  • Review follow-up added 3 more triples: set-op (UNION) top-level order, parenthesized whole query, and unparseable gold_sql → insensitive fallback.

AST-detection unit tests

  • Parametrized cases for top-level vs subquery / CTE / set-op order, plus the parenthesized-query unwrap.
  • Guards that 'ORDER BY x' inside a string literal is not detected (a regex scan would false-positive), and asserts the new default rule.

The gold SQL's AST — not a string scan — decides whether row order is significant. When it isn't, both sides are sorted with a total, exception-free key; when it is, rows are left as returned so an order error is caught. Either branch transforms gold and candidate identically, then the unchanged gold.rows == candidate.rows check produces the verdict.
