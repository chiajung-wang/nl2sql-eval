Budget-aware adaptive retrieval gate

Author: Chia-Jung Wang (@chiajung-wang) Issue: #76 Branch: step-6-follow-up/issue-76-adaptive-gate → main

1 Overview

The loop closing: #75 measured where retrieval pays, so #76 makes the system retrieve only there. A deterministic gate — full dump when the schema fits the budget, RAG when it overflows.

Step 6's schema-RAG capped at max_tables and so could drop a needed table even when the whole schema would have fit the prompt. The gate removes that risk structurally: if the full schema fits a configured schema-token budget (a cost/latency policy, not the context limit), dump it; only when it overflows does retrieve select the relevant tables. The decision is a pure token-threshold comparison — no LLM, config-driven (DEFAULT_SCHEMA_TOKEN_BUDGET = 2048), import-shared between demo and harness.

And like #75, the headline is a measurement-discipline one: the pass@1 deltas are within sampling noise, so the honest claim is structural (no-regret), not an accuracy lift.

Within noise, by design no-regret. The +0.025 vs always-RAG and +0.000 vs naive both sit within the ~0.05 sampling-noise floor measured in #75 (temperature>0, 40 questions) — so this is not a significant pass@1 lift. Tellingly, the dramatic Step-6 RAG loss (−0.125) did not reproduce this run (always-RAG trailed naive by only 0.025), confirming the original gap carried sampling variance too. The gate's real value is structural: it makes the deterministic cost/accuracy-optimal choice per db — never paying the cap's table-drop risk where the schema fits, retrieving only where the budget is exceeded — and measured here it never does worse than either baseline.

Deterministic, threshold-driven, no LLM. budget_tokens=None disables the gate (the prior always-RAG path) — fully backwards-compatible. The loop-aware re-retrieve (#46) still widens on a not-found error, bypassing the gate on re-passes.
