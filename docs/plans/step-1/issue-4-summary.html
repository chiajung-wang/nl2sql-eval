1 Overview

Implements Issue 4 — the thinnest hand-rolled NL→SQL path: a linear question → generate → execute → return pipeline with no guardrails, retrieval, self-correction, framework, harness, or UI. One provider is called directly so the measurement seams can be wired in around a minimal-but-real workload.

Generation makes a single direct Anthropic SDK call with the full payments schema dumped inline and the prompt loaded from an externalized Jinja template; execution runs the candidate SQL via SQLAlchemy against the payments Postgres db. The key invariant carried in early: the observability span sees only result shape (row/column counts), never raw rows — raw PII never reaches logs or traces (CLAUDE.md §5.3).

2 Key changes

Pipeline stages (logic)

  • generate.py — one direct Anthropic messages.create call, default claude-sonnet-4-6; schema inline; injectable + lazily-constructed client so import needs no API key.
  • execute.py — SQLAlchemy execution against the payments db (engine passed in); errors captured, not raised; only row/column counts hit the span.
  • graph.py — linear run_pipeline wiring generate → execute (no loop/conditionals) plus a dev smoke __main__.

Prompts & obs

  • prompts/generate/v1.jinja — generation prompt externalized as a versioned template; schema + question are Jinja variables. Never inlined (CI diffs prompts/).
  • Each stage emits a structured event through the Issue 1 observability seam.

Tests

  • tests/test_pipeline_loop.py — CI-safe coverage with in-memory SQLite + an injected fake client: template externalization, SQL fence-extraction, generate/execute/wiring, and a regression proving raw cell values never reach logs.

Tooling & docs (scaffolding)

  • pyproject.toml / uv.lock — add anthropic + jinja2.
  • .env.example / README.md — document ANTHROPIC_API_KEY and the smoke command.
  • llm/__init__.py — keeps the LiteLLM (Step 7) placeholder explicit.
