1 Overview

The batch runner that turns the Step-1 pipeline + Step-2 comparator into a repeatable measurement job — validated on trusted ground before BIRD.

For each question the harness runs the import-shared pipeline (never a copy — no drift from the demo), scores the result via the canonicalized comparator, and buckets it into exactly one terminal state. Aggregation emits pass@1 — the only meaningful metric with no self-correction yet. The run_one callable is injected, so the harness logic runs offline in tests (stubbed) and binds the real pipeline in the live entrypoint.

The discipline of the step: if the harness can't correctly score the payments questions whose answers we know cold, it has no business scoring BIRD. So this slice ends with a live self-check, not a benchmark number.

2 Key changes

eval/harness.py — the batch runner

  • Case (db-tagged question + gold), run_batch, and score_run.
  • run_one is an injected Case → RunState — live entrypoints bind the shared run_pipeline; tests stub it. No forked pipeline logic.
  • The terminal-state classifier extended to reach WRONG_ANSWER via the comparator's verdict — back-compatible arity so the Step-1 proof still works.

eval/metrics.py — aggregation

  • CaseResult + BatchReport: pass@1, the terminal-state mix, and pass@1-by-difficulty.
  • Aggregation only — never holds row values; the note field carries the comparator's reason or error text, not data.

eval/eval_payments.py — live job

  • Loads .env (python-dotenv), builds the seeded-Postgres engine + schema, maps verified questions to cases, runs the batch, prints pass@1.
  • Runnable as a job: uv run python -m eval.eval_payments.

tests/test_harness.py — offline proof

  • Stubbed runner: classification (success / wrong_answer / error), aggregation, empty-batch safety.
  • Proves the batch routes through the order-aware comparator — not a string/exact check.
