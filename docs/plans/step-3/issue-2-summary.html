1 Overview

The BIRD dataset adapter and the frozen evaluation slice that anchors every future number.

BIRD ships SQLite, file-per-db: each question is tagged with its database and runs against that db only (single-db per run; cross-db routing is out of scope). The loader resolves and opens each tagged db read-only, dumps its CREATE TABLE schema for the naive prompt, and materializes result sets for scoring via the Step-2 comparator.

The slice is the trust anchor: frozen (checked-in ID list), seeded (one RNG seed → one reproducible slice), stratified (difficulty mix preserved), and drawn only from small-schema dbs — because with no retrieval yet, the whole schema is dumped into the prompt, and large schemas would overflow context and tank accuracy for reasons unrelated to generation. Small-schema-first keeps the baseline honest.

2 Key changes

loader.py — tagged-db adapter

  • load_dev_questions, db_path, get_engine (SQLAlchemy, read-only).
  • schema_text — the naive CREATE TABLE dump (stable, name-ordered).
  • run_query → comparator-shaped {columns, rows}; table_count as the schema-size proxy.

slice.py — seeded, stratified selection

  • Pure logic: filter to dbs with ≤ max_tables, then largest-remainder difficulty-stratified sampling under a fixed seed.
  • Deterministic — same inputs + seed → same IDs. Tested both ways.
  • python -m eval.datasets.bird.slice regenerates the frozen file.

slice_step3.json — the frozen list

  • 50 question_ids + a _meta provenance block (criteria, eligible dbs, mixes, date).
  • Committed; the benchmark data itself stays gitignored.

test_bird.py — offline + real-data

  • Pure selection + synthetic-sqlite loader tests need no download.
  • Real-data tests (skipped without data) prove load → execute gold → score and validate the slice.
