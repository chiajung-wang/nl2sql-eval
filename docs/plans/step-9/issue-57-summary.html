1 Overview

Build the foundation prompt-CI stands on. Step 9's headline is a CI job that re-runs the eval whenever a prompt changes and posts the pass@1/pass@k deltas. For that signal to be trustworthy, two things have to be true first: a prompt edit must produce a legible diff, and every number must pin to the exact prompt bytes that produced it. This issue delivers both.

The prompts were already externalized Jinja templates (CLAUDE.md §4). This makes them a clean, version-controlled foundation: a single registry module owns loading, the active version, and a content fingerprint; the static scaffold lives once and version files extend it, so a change shows as a tight diff rather than a whole-file rewrite.

2 What the registry surfaces

nl2sql.prompts is the single place that knows where templates live, which version is active, and how to render them. The Jinja environment, the version string, and the fingerprint stop being scattered module constants.

4 Byte-identical refactor

Moving the scaffold into a partial is a refactor, not a prompt change — so the rendered prompt must not move a single byte, or the "pass@1 unchanged, no rerun needed" claim is false. A golden-string test asserts the active template renders exactly what the prior single-file v3 did, with and without the correction block.
