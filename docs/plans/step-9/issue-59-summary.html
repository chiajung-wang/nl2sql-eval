2 The reasonable-looking edit

A single clean {% block rules %} change over the shared scaffold — the kind of edit a developer makes wanting the model to show its work:

# prompts/generate/_demo_regression.jinja  (never active; v3 stays active)
{% raw %}{% block rules %}{% endraw %}- First, briefly explain your approach in one or two sentences.
- Then provide the SQL query that answers the question.
- Use only the tables and columns defined in the schema below.
- Use {{ '{{' }} dialect {{ '}}' }} syntax.
- The query must be read-only: a single SELECT statement.{% raw %}{% endblock %}{% endraw %}

It relaxes the load-bearing "return ONLY the SQL" rule. The model now prefaces its answer with prose, the fence stripper can't unwrap it, the candidate is no longer valid SQL — and the deterministic guard rejects it. Every question fails.

4 A latent crash, surfaced and fixed

Running the harmful prompt exposed a real bug. When the model's prose leaked a stray markdown fence, the candidate was untokenizable — sqlglot raised TokenError (a sibling of ParseError) from the guard's parse, which the guard didn't catch. The run crashed instead of bucketing into a terminal state — a direct violation of the every-run-terminates invariant (CLAUDE.md §3).

# src/nl2sql/pipeline/guard.py · _parse_statements
-        except ParseError:
+        except (ParseError, TokenError):   # unparseable → reject, never crash

Now an untokenizable candidate is a clean parse_error guardrail rejection. Locked by test_untokenizable_sql_is_rejected_not_crashed — the deterministic guard core stays sqlglot-AST-only, no regex, no LLM (§4/§8).
