Schema linking by task-alignment — let the generator vote with its query

Author: Chia-Jung Wang (@chiajung-wang) Issue: #138 Branch: step-12/issue-138-schema-linking → main Source: Shkapenyuk et al., arXiv:2505.19988v2 §3 (AT&T #1 BIRD)

1 Overview

Don't ask the model which tables are relevant — ask it to write SQL, then read the tables it used. The paper's contrarian finding: LLMs are poor at directly naming relevant tables (a task they were never trained on) but good at generating SQL. So this adds an alternative initial-retrieval strategy to the lexical schema-RAG in retrieve.py: generate SQL against a couple of schema variants, harvest the tables that SQL references (sqlglot AST), and union them. Recall over precision — "better too many fields than too few."

2 The idea — task-alignment vs. lexical RAG

Lexical schema-RAG scores and drops tables to fit a budget — precision-biased, and it can silently drop a table the query actually needs. Task-alignment inverts the question: it lets the generated SQL nominate the tables, then keeps the real ones.

question→ generate SQL vs focused schema & generate SQL vs full schema → harvest tables (AST)→ drop hallucinated→ ∪ = linked schema

The union is returned in the index's declaration order — the canonical render order — so only which tables differ between strategies, never the rendering. The harvested set lands on state.retrieved_tables exactly as RAG's does, so the harness's retrieval-recall metric (PRD rule 7) scores both strategies identically.

3 The deterministic core — tables_in_sql

Harvesting is pure sqlglot AST, never a string scan (CLAUDE.md §4). One canonical extractor, shared by the linker and the recall metric — no fork, so both read tables the same way.

# sqlglot exp.Table nodes — an alias, a column named like a table, or
# the word "from" inside a string literal can't fool it. CTE names excluded:
# a retriever can never surface a WITH block, so counting it would distort recall.
tables_in_sql("SELECT * FROM orders JOIN customers ON ...")      # {orders, customers}
tables_in_sql("WITH recent AS (SELECT * FROM orders) SELECT * FROM recent ...")
                                                        # {orders} — 'recent' CTE dropped
tables_in_sql("this is not sql at all")                       # set() — never raises

A malformed generation degrades (empty set) rather than raising; the SQLite→generic dialect fallback mirrors the comparator's tolerant parse. eval/metrics.py now delegates its gold-table extraction here — the recall metric and the linker are one definition.

4 Degrade, never starve

situationbehaviour
A variant generation raises (provider blip)Non-fatal — the other variants still contribute; the run continues.
Generated SQL names a table not in the schemaDropped — a hallucinated name can't be "retrieved".
No variant yields any in-schema tableFalls back to the lexical-RAG focused set — the generator is never handed an empty schema.
Linking spends extra generationsPriced — each linking call's tokens/cost fold into run.meta, so the harness accounts the lift's cost.

The linking generations use a throwaway RunState per variant, so they never clobber the answer state — and stay distinct from #142's candidate voting (these vote on schema, not answers).

5 Review fix — validate link_strategy (Standards JC2)

The two-axis review found no hard violations. The one actionable judgement call: a typo'd or unrecognized link_strategy silently fell back to lexical RAG — which would misattribute a measured A/B (the run claims task-alignment linking but actually ran the baseline), violating the traceability rule (CLAUDE.md §6).

# run_pipeline now rejects an unknown strategy up front —
# mirroring link_tables' own raise on an unknown *variant* (equal strictness).
if link_strategy is not None and link_strategy not in LINK_STRATEGIES:
    raise ValueError(f"unknown link_strategy: {link_strategy!r}")

Regression test asserts the reject happens before any generation is attempted. None (no linking) stays the default and is always allowed.
