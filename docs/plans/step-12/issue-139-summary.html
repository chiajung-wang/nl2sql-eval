Deterministic bad-construction checks — a correction signal, not a gate

1 Overview

Some wrong answers have a mechanical shape a deterministic check can catch. Where the table-selection cluster (#122) is a model-capability wall, the paper's bad-construction checks are concrete, AST-detectable defects — the rare Step-12 lever with a non-model mechanism. Three sqlglot-AST checks land in a new soundness stage: same shape as the guard, but a correction contract — a hit feeds a fix back to the generator, it never terminally rejects.

2 The three checks — each a wrong-answer shape

checkflagswhy it's wrong
null_orderingmin(f) / ORDER BY f ASC LIMIT over an unguarded columnA NULL sorts first ascending — the top row / minimum can be NULL-driven. MAX/DESC are safe (NULLs sort last).
minmax_subquery= (SELECT MIN/MAX(x) …), uncorrelated onlySelecting the extreme-value row by a scalar subquery is what ORDER BY x LIMIT 1 expresses more reliably. A correlated subquery needs the form — not flagged.
field_catenationa || b / CONCAT(a,b) of ≥2 distinct fieldsFuses values the question wants as separate columns — a wrong result shape. A column-plus-literal is not flagged.

Checks judge the outermost query — the result the user receives — so a scalar MIN(x) building-block subquery (a common, correct idiom) is never flagged. Detection is pure sqlglot AST: a column literally named minimum, or the word from in a string literal, can't fool it.

3 The contract — a correction signal, never a lost run

This is the same AST-check shape as guard.py but the opposite contract. A guard hit is a terminal GUARDRAIL_REJECTED; a soundness hit is recoverable.

guard allow→ soundness→ flag + budget left→ correct_soundness→ generate (retry)
soundness→ flag + budget spent→ execute anyway | clean→execute

So a false positive costs at most a wasted retry, never a dropped answer — a soundness heuristic must never lose a run (CLAUDE.md §5). Retries share the one capped budget (the ceiling was widened for the two extra supersteps); feedback reuses the existing correct.py channel.

4 The deliverable — fixture catch rate + false-positive rate

The primary, offline deliverable (PRD rule 11): fixtures/soundness/ pairs positives with near-miss negatives — the cases that separate a real check from an over-firing one.

# fixtures/soundness/ — replayed through check_soundness_sql
catch_rate           = 1.000  (9/9  positives flagged)
false_positive_rate  = 0.000  (0/12 near-miss negatives flagged)

# near-miss negatives that must NOT flag:
MIN(price) WHERE price IS NOT NULL     # guarded
MAX(salary)                            # NULLs sort last
ORDER BY score ASC                     # no LIMIT — full list
price = (SELECT MIN(p2.price) … WHERE p2.cat = p.cat)   # correlated
name || ' (active)'                    # column + literal

Honest caveat (surfaced in review): SQL MIN ignores NULLs, so the bare-min(f) positives encode the paper's/spec's hazard claim rather than objective SQL truth — they hold on the BIRD questions where the gold query itself adds … IS NOT NULL. The ORDER BY … ASC LIMIT positives are the unambiguous hazard. So 9/9 is a catch rate against a spec-inherited ground truth for ~3 of the 9, which the deferred live A/B adjudicates.
