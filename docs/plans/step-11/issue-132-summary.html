1 Overview

Ship the step's biggest win as a switch, not a paragraph. Step 11's largest measured lift was the model swap — gemini-3.5-flash at pass@1 0.520 / 0.580 BIRD (#124), +0.10 over the sonnet baseline, no slice-overfitting risk. But it lived only in README prose: a reader had to hand-assemble MODEL=… + MAX_TOKENS=…. This makes each config a named bundle the harness and the demo select identically via RUN_CONFIG — the measurement apparatus is the product, so a banked result becomes one switch.

2 The design — one source of truth, MODEL still wins

propertyhow
Single source of truthsrc/nl2sql/run_config.py defines RunConfig(model, max_tokens) + the two named bundles. It imports nothing from the pipeline, so generate.py sources its DEFAULT_MODEL/DEFAULT_MAX_TOKENS from it without an import cycle.
Import-shared, no forkHarness (eval/model_select.py) and demo (apps/demo/app.py) both resolve through active_config() — RUN_CONFIG=accuracy flips both. Tightens CLAUDE.md §3.
PrecedenceAn explicit MODEL/MAX_TOKENS still wins over the bundle; with nothing set the default is list-priced = the prior pin ⇒ a clean checkout is byte-identical.
Default not repinnedDEFAULT_CONFIG = LIST_PRICED (direct, list-priced sonnet) — repinning the OpenRouter model globally would forfeit clean cost accounting (#117 objection stands).

3 Verification — reproduction within the noise floor

The check isn't a new lever — it's reproduction. A live paid run resolved the accuracy bundle and re-measured the dev slice:

# RUN_CONFIG=accuracy → gemini-3.5-flash + MAX_TOKENS=4096
pass@1 0.480 (24/50) strict / 0.520 (26/50) BIRD set-semantics

That's within the ~0.05 sampling-noise floor of #124's 0.520/0.580 (a reasoning model at temperature>0), and the top config against the 0.420 sonnet baseline — recorded honestly in RESULTS.md as a re-sample, not an exact reproduction. A real-world wrinkle is documented: a .env that pins MODEL (the cheap dev workhorse) shadows RUN_CONFIG by design — clear it to let accuracy take effect.

4 Focused review — the decorative field both axes caught

The two-axis review (Standards + Spec) converged on one genuine item: RunConfig carried a prompt_version field that was never read, hardcoded a stale "v3" literal contradicting the registry's "generate/v3", and whose docstring falsely claimed it lands in RESULTS.md rows — exactly the duplication CLAUDE.md §4 exists to prevent.

# every runner already sources the version from the prompt registry, not a config
write_results_row(..., prompt_version=PROMPT_VERSION)  # nl2sql.prompts, the §4 SoT

Fix: drop the field, reduce RunConfig to the two knobs that actually differ between axes (model, max_tokens), and document why prompt version (registry-owned) and dialect (a per-dataset input) are deliberately not config fields.
