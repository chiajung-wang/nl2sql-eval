Dangerous-op blocking

Author: Chia-Jung Wang (@chiajung-wang) Issue: #33 Branch: step-4/issue-2-dangerous-op → step-4/guardrails-and-redteam

1 Overview

A second guard rule for the constructs read-only misses: side-effecting and injection-shaped SQL that isn't a data write — but is never a valid answer to a question.

Read-only enforcement (Issue 1) catches DML/DDL. But a candidate can be dangerous without writing a row: a stacked query (SELECT …; DROP …), an ATTACH that reaches across the single-db boundary, a PRAGMA writable_schema=ON that unlocks the schema to bypass protections. The dangerous_op rule rejects all of these — sqlglot AST-typed, never a regex — and slots into the same fail-fast rule pipeline behind read-only.

Two deliberate default-deny calls: all PRAGMA (read- vs write-PRAGMA can't be separated reliably on the AST, and none is a valid answer) and all unmodeled Commands (engine state we don't understand — VACUUM, SET — we won't run). Safer and simpler than enumerating a blocklist that the next obscure verb defeats.

Rules run in order, first match wins. A stacked candidate ending in a write is pinned to read_only because it fires first — precedence is deterministic and tested.
