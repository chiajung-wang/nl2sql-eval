Correction loop (execution-error feedback) + capped retry budget

Author: Chia-Jung Wang (@chiajung-wang) Issue: #42 Branch: feat/step-5-issue-1-correction-loop → main

1 Overview

The Step-5 tracer bullet: the single-shot generator becomes an agent. On an execution error, the failed SQL and the database error are fed back into a fresh generation — inside a configurable, capped retry budget.

Until now the pipeline was a straight line: generate → guard → execute → return. One shot, one verdict. This issue closes the loop. When execute sets state.error, the new correct stage captures the broken candidate and the engine's message, and the graph regenerates with that failure rendered into the prompt — repeating until the candidate succeeds or the max_attempts budget is spent. The cap is the point: it makes recovery bounded, so the cost/latency it buys is a lever we can measure rather than a runaway.

This is deliberately plumbing, not a number. It establishes the full vertical — error → correct → regenerate → capped loop → terminal state — so the twin-metric work (#43) only has to read the loop's attempt counts, and the RESULTS.md pass@1→pass@k gap (#44) falls out of running it twice: budget 1 vs budget k.

2 Key changes

correct.py — the new stage

  • Stages the prior failure onto state.correction as structured {sql, error} — data only, no prompt strings (the wording lives in the template, §4).
  • Clears error/result_* so the next cycle is scored on its own outcome, never the discarded attempt's.
  • No-op when there is no error to feed back — a stray call can't fabricate a correction.

graph.py — the capped loop

  • generate → guard → execute → correct loop under max_attempts (budget = max(1, max_attempts) clamps bad input).
  • Returns on a clean execute, a guard rejection (terminal here), or budget exhaustion.
  • Default max_attempts=1 ⇒ the existing single-shot pass@1 behavior, untouched.

prompts/generate/v3.jinja

  • Optional {%- if correction %} block renders the prior SQL + DB error.
  • With correction off the output is byte-identical to v2 — pass@1 cannot drift. PROMPT_VERSION → generate/v3.

state.py & harness.py

  • state.py: max_attempts + correction — data only.
  • harness: the terminal-state split (the classifier stays in the harness, §3).

  classDef ok fill:#bbf7d0,stroke:#16a34a,color:#14532d;
  classDef live fill:#c7d2fe,stroke:#4f46e5,color:#1e1b4b;
  classDef term fill:#fde68a,stroke:#d97706,color:#7c2d12;
  class OK ok; class C live; class GR,RE,EF term;

The error split is keyed off state.attempts: the loop only returns an errored run after the budget is spent, so attempts > 1 ⇒ correction ran and still failed (retry_exhausted), while a single-shot failure — pass@1 mode, or a generation gap — keeps the prior execution_error_final bucket. The enum lives in state.py; the classifier lives in the harness (§3).
