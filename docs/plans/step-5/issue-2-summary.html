Twin metrics: pass@1 AND pass@k (+ attempts/cost/latency)

Author: Chia-Jung Wang (@chiajung-wang) Issue: #43 Branch: feat/step-5-issue-2-twin-metrics → main

1 Overview

Self-correction is only worth measuring if you also measure what it costs. This issue teaches the harness to report both pass@1 and pass@k over the same slice — and the cost and latency the gap between them buys.

#42 gave the pipeline a correction loop. But a loop that silently retries until it stumbles onto the right answer makes accuracy look good while latency and cost quietly balloon — that's the exact pitfall the plan warns about. The defense is to never report the lift without its price. So the harness now runs the slice twice — correction off (single shot, pass@1) and correction on (the capped budget, pass@k) — and a TwinReport computes the gap, the recovery rate (of the questions pass@1 got wrong, how many pass@k saves), and the added attempts, latency, and dollars.

Cost is real dollars, not a hand-wave: a small, dated price table turns the token counts each run accumulates into USD. This is deliberately the machinery, not the number — the live BIRD twin run that produces the committed pass@1→pass@k row is #44.

2 Key changes

eval/cost.py — token → USD

  • Dated price table (Claude API table, cached 2026-06-04): sonnet-4-6 $3/$15, haiku-4-5 $1/$5, opus-4.x $5/$25 per 1M.
  • cost_usd() returns None for an unpriced model — surfaces as "unavailable", never a fabricated number.
  • Costs are logged next to their token totals, so a price revision re-prices the future, not the past.

metrics.py — the twin report

  • CaseResult gains attempts / input_tokens / output_tokens / latency_ms.
  • BatchReport aggregates them + cost_usd(model); mode-neutral accuracy (with pass_at_1 kept as an alias).
  • TwinReport: gap, recovery rate, added attempts/latency/cost.

harness.py — capture & orchestrate

  • run_batch times each run (wall-clock, all attempts) and reads attempts/tokens off the RunState.
  • run_twin() runs the same cases off-then-on; the live entrypoint just supplies a factory(max_attempts).

generate.py — totals, not snapshots

  • Accumulate token usage onto state.meta across retries, so pass@k is priced on the run's total tokens — a retry spends them twice.

Both batches run the same cases through the import-shared pipeline and the same comparator; only the retry budget differs. recovery_rate aligns the two by case_id — order-independent. The cost lever is explicit: pass@k's added dollars are passk.cost_usd(model) − pass1.cost_usd(model).

4 What the report says, in plain terms

lift, against its price  — a worked example from the unit tests

Questionpass@1 (off)pass@k (on)
q1correct · 1 attemptcorrect · 1 attempt
q2wrong · 1 attemptrecovered · 2 attempts
q3wrong · 1 attemptwrong · 3 attempts (budget spent)

pass@1 = 0.33 → pass@k = 0.67 (gap +0.33); recovery of initial failures 0.50 (1 of 2 failures saved); added attempts +3, with the extra latency and dollars reported alongside. The accuracy gain is never shown without the cost that bought it — the guard against silent, expensive retrying.
