Schema-RAG retrieve stage — relevant tables, not the full dump

Author: Chia-Jung Wang (@chiajung-wang) Issue: #45 Branch: step-6/issue-45-schema-rag-retrieve-stage → main

1 Overview

The Step-6 tracer bullet: stop dumping the whole schema into the prompt. Build an index over the db's tables and retrieve only the ones relevant to this question — wired end-to-end through the import-shared pipeline.

Through Step 3 the generator saw the entire schema — every CREATE TABLE in the db, whether or not the question touched it (the naive-dump baseline). That is fine on a 4-table payments db and fatal on BIRD's large schemas, where the relevant 2 tables drown in 40. This issue adds the retrieve stage: a SchemaIndex of columns/types, foreign-key edges, and a few sample values per column, scored against the question by deterministic lexical overlap, so generate receives only the tables that matter.

Sample values are the quiet win: knowing status ∈ {failed, settled} changes the SQL, and that signal never appeared in a bare DDL dump. It rides along in the rendered block now. This is the vertical the rest of Step 6 hangs off — the loop-aware re-trigger, the recall metric, the table-scope guard, and the lift number all build on the table names this stage records.

2 Key changes

schema_index/ — the store + retriever

  • build_schema_index(engine) introspects columns/types, FK edges, and sample values via SQLAlchemy's Inspector — portable across SQLite (BIRD) and Postgres (payments).
  • Deterministic relevance: lexical token overlap over name + column + sample-value tokens; name hits weigh more than value hits. No embeddings, no network, no LLM.
  • FK-neighbour expansion pulls in join targets; the set is capped at max_tables with ranked picks keeping priority. No lexical signal ⇒ degrade to the full schema.

pipeline/retrieve.py — the stage

  • Selects + renders the focused schema for state.question.
  • Records the chosen tables on state.retrieved_tables — the hook the recall metric reads.
  • Span logs only table names and counts — schema metadata, never result rows (§5.3).

graph.py — two schema sources

  • run_pipeline takes exactly one of schema= (naive baseline) or schema_index= (retrieval) — a ValueError guards against both/neither.
  • Retrieve runs once up front; the loop-aware re-trigger is the next slice.
  • Import-shared: harness and demo build the index and call retrieve the same way.

state.py

  • retrieved_tables: list[str] | None — data only, no classifier logic.

The retriever scores the index's tables against the question and hands generate only the selected ones. The selected names are recorded on the state so a later slice can score retrieval recall against the gold query's tables. The re-trigger that feeds a not-found error back into retrieve (closing the loop on the dashed edge) is Issue 2.

4 What the generator sees now

A focused block per retrieved table — DDL plus the FK edges and sample values the naive dump lacked:

-- retrieved for: "count settled payments"
CREATE TABLE payments (
  id INTEGER,
  status TEXT,
  order_id INTEGER,
  FOREIGN KEY (order_id) REFERENCES orders
);
-- sample values:
--   status ∈ {failed, settled}

The settled value is what lets the model write WHERE status = 'settled' instead of guessing. Sample values come from a bounded SELECT DISTINCT … LIMIT, so a low-cardinality enum is captured wherever its values sit in the table — not just within an arbitrary row prefix.
