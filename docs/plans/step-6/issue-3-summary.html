Retrieval-recall metric

Author: Chia-Jung Wang (@chiajung-wang) Issue: #47 Branch: step-6/issue-47-retrieval-recall → main

1 Overview

Measure the failure that can't be fixed at runtime: valid SQL over the wrong tables — no error, a wrong-but-unsuspicious answer that accuracy alone never sees.

Schema-RAG (issues #45/#46) selects relevant tables instead of dumping the whole schema. But a retriever that silently drops a needed table produces a query that runs clean and answers wrong. You can't fix that at runtime without solving Text-to-SQL — so the deliverable is to measure it. This issue adds the retrieval-recall axis: of the tables the gold query actually uses, what fraction did the retriever surface?

recall = |retrieved ∩ gold| / |gold|

2 Key changes

gold_query_tables(sql)

  • Base tables the gold references, from exp.Table nodes — never a string scan (CLAUDE.md §4). Aliases, string literals, and the word FROM can't fool it.
  • CTE names excluded: a WITH reference parses as a Table, but the retriever can never "retrieve" a CTE — counting it would deflate recall.

retrieval_recall(retrieved, gold)

  • |retrieved ∩ gold| / |gold|, case-insensitive.
  • None when retrieval didn't run (naive-dump path) or the gold has no tables — those cases are excluded from the aggregate, not counted 0 or 1.

Aggregation + reporting

  • BatchReport.mean_retrieval_recall + n_with_recall; a summary_lines line alongside accuracy (omitted on the naive-dump path).
  • The harness populates per-case recall from state.retrieved_tables.

Recall, not precision

  • Extra retrieved tables don't lower recall — coverage of the gold is what matters; prompt cost is a separate axis.

Accuracy can't tell a wrong-schema answer from a right one — both "run." Recall exposes the dropped table directly, so the silent failure becomes a measured quantity.

4 Review fix — the CTE miscount

An independent review caught a real correctness gap: a CTE reference parses as an exp.Table, so WITH t AS (… atom … bond …) SELECT * FROM t counted t as a gold table — scoring a perfect retrieval as recall 0.667, not 1.0. A CTE shadowing a real table name was the inverse error. Fixed by subtracting exp.CTE names from the gold set, with CTE, CTE-shadow, and table-valued-function regression tests.
