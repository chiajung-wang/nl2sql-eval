Thin demo UI that reveals the wrapper

Author: Chia-Jung Wang (@chiajung-wang) Issue: #62 Branch: step-10/issue-62-demo-ui → main

1 Overview

Show the machinery, don't hide a chatbot. The demo's whole job is to make the wrapper visible — the guardrail decision and why, the retry count the correction loop spent, the cost the run burned, and the terminal state it bucketed into — for one question, live.

The discipline that keeps it honest: it imports the same run_pipeline the harness measures and the harness's own classify_terminal_state — never a fork — so the demo can't drift from the numbers. And it only ever shows the presented (redacted) result; the raw verified rows the harness scores have no field on the view to leak through.

Streamlit is hard to unit-test, so all logic lives in the testable runner.py (run_demo + the badge map + dataset parsing); app.py is a thin shell that builds engines and renders. The core is covered with a fake client + in-memory SQLite — no Streamlit, no network, no key.

4 Honest by construction

  • No fork (CLAUDE.md §3). run_demo calls the import-shared pipeline and the harness's own classifier — duplicating either would be the violation.
  • No raw PII (§3/§5). DemoView has no result_rows/result_columns field at all — only presented_*. A test asserts both the masked value and the structural absence of any raw-row field.
  • Isolated deps. streamlit lives in its own demo group; the core and the whole test suite run with it absent (verified).
